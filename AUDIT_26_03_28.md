# Sanctum Audit Report
**Date:** March 28, 2026 | **Status:** Active Development (Beta/RC) | **Overall Security Posture: 7.5/10**

---

## Project Overview

Sanctum is a **privacy-first, zero-knowledge personal vault** built with React 19 + Firebase. All sensitive data is encrypted client-side using AES-256-GCM before storage — the server only ever sees opaque encrypted blobs. The master key is held in memory only and never persisted.

**Live:** `https://sanctum.aks-hub.web.app`

## Cryptographic Architecture

| Purpose | Algorithm | Parameters |
|---|---|---|
| New Vault KDF | Argon2id | 64 MB memory, 3 iterations, 256-bit output |
| Legacy KDF | PBKDF2 | 600k iterations, SHA-256 (auto-migrates to Argon2id) |
| Data Encryption | AES-256-GCM | 12-byte random IV per operation |
| Collaboration Keys | RSA-4096-OAEP | Per-doc AES key wrapped per collaborator |
| 1:1 Chat | ECDH P-256 + AES-256-GCM | Ephemeral per-message keys (forward secrecy) |
| Group Chat | RSA-4096-OAEP + AES-256-GCM | Shared group key, RSA-wrapped per member |
| Public Share Links | AES-256-GCM | Key in URL fragment (never sent to server) |

### Authentication & Vault Unlock Flow

1. User signs in via Google OAuth (`GoogleAuthProvider`)
2. Firebase Auth issues `idToken` + `refreshToken`
3. LockScreen appears (vault is locked)
4. User enters passkey (≥8 characters)
5. Vault unlock:
   - Fetch user doc from Firestore: `encryptionSalt`, `encryptedMasterKey`, `kdf`
   - Derive wrapper key: Argon2id(passkey, salt) or PBKDF2 (legacy)
   - Decrypt master key JWK with wrapper key
   - Validate by decrypting `encryptedValidator` (must return `{ check: "VALID" }`)
   - If PBKDF2 → auto-migrate to Argon2id
6. Master key held in React state (VaultContext.cryptoKey) — memory only, never persisted
7. Auto-lock on configurable inactivity timeout (5m/15m/1h/Never) + instant lock on tab hidden

### Encrypted vs. Unencrypted Fields

- **Encrypted:** Titles, body text, passwords, URLs, tags, attachments, all content metadata
- **Unencrypted (structural):** `isPinned`, `type`, `parentId`, `order`, timestamps, `itemCount`, `completed` status
- **Rationale:** Structural metadata required for Firestore queries; content encrypted; activity log intentionally plaintext for audit visibility

## Security Findings

### Critical Issues

---

#### CRIT-1 — New Vault Uses PBKDF2 Instead of Argon2id

- **File:** `src/services/vault.js:52`
- **Description:** `initializeVault()` calls `deriveKeyFromPasskey()` (PBKDF2) instead of `deriveKeyArgon2id()`. All new users start with the weaker KDF. It auto-migrates only on the next unlock, not transparently at initialization.
- **Impact:** New vaults are GPU-crackable until first re-unlock. Contradicts the documented "Argon2id is used for all new vaults" guarantee.
- **Fix:** Replace `deriveKeyFromPasskey()` with `deriveKeyArgon2id()` in the vault initialization path.

---

#### CRIT-2 — Legacy Firebase Storage Rule Allows Cross-User Access

- **File:** `storage.rules:42-45`
- **Description:** A catch-all rule allows any authenticated user to read/write under generic top-level folder names (`notes`, `markdown`, `research`, etc.) without UID ownership verification.

```
match /{folder}/{allPaths=**} {
  allow read, write: if isAuthenticated() && folder in ['notes', 'markdown', ...];
}
```

- **Impact:** Any authenticated Sanctum user can read or overwrite another user's files stored under these paths. Client-side encryption limits plaintext exposure but metadata and storage costs are exposed.
- **Fix:** Remove the legacy catch-all rule entirely. Migrate all files to `/artifacts/{appId}/users/{uid}/` scoped paths.

---

#### CRIT-3 — Attachment Decryption Ignores Workspace Key Context

- **File:** `src/services/collaboration.js:86-123`
- **Description:** Attachments are always decrypted with the personal master key. If the attachment was encrypted in a workspace context (using the workspace AES key), decryption silently fails.
- **Impact:** Shared workspace attachments are inaccessible to collaborators or produce corrupt data.
- **Fix:** Accept a `sourceKey` parameter in the attachment decrypt path, or detect the encryption context (personal vs. workspace) before decrypting.

---

### High Severity

---

#### HIGH-4 — Race Condition in Document Sharing

- **File:** `src/services/collaboration.js:377-438`
- **Description:** The initial share doc write and the file reference update are separate, non-atomic Firestore operations. A collaborator loading the document between these two writes sees broken file references.
- **Fix:** Wrap both writes in a Firestore transaction.

---

#### HIGH-5 — Concurrent Edit Overwrites During Key Rotation

- **File:** `src/services/collaboration.js:285-338`
- **Description:** Collaborator removal triggers full re-encryption from a snapshot of the document taken at rotation start. Any concurrent edit between snapshot and write is silently overwritten.
- **Fix:** Wrap re-encryption in a Firestore transaction using `runTransaction()` with optimistic locking.

---

#### HIGH-6 — `resetUserVault()` Incomplete — Missing Collections

- **File:** `src/services/vault.js:12-13`
- **Description:** The vault factory reset only deletes 8 hardcoded collections. Missing: `markdown`, `authenticator`, `contacts`, `reminders`, `research`, `devices`, `activity_log`, shared subcollections, workspace subcollections.
- **Impact:** User data persists after a factory reset. Violation of user data deletion expectation.
- **Fix:** Enumerate all collections from AppRegistry. Implement recursive subcollection deletion. Chunk batch deletes into ≤500 operation batches.

---

#### HIGH-7 — Public Shared Notes Have No Expiration

- **File:** `firestore.rules:21-25`
- **Description:** `shared_notes` documents accumulate in Firestore indefinitely. No TTL field, no expiration rule, no cleanup mechanism.
- **Impact:** Sensitive data shared publicly remains accessible forever unless manually revoked.
- **Fix:** Add `expiresAt` timestamp field at creation. Deploy a Cloud Function (scheduled or triggered) to purge expired notes.

---

### Medium Severity

| ID | Issue | Location | Fix |
|---|---|---|---|
| MED-8 | No passkey confirmation on change — a typo could permanently lock the user out | `src/apps/settings/Settings.jsx` SecurityTab | Add a confirm-passkey input step before committing the change |
| MED-9 | `fileId` not sanitized for `../` sequences — potential path traversal in Storage paths | `src/services/firebaseStorage.js:8-18` | Validate fileId format; reject any value containing `..` or `/` |
| MED-10 | Activity log is stored plaintext — reveals usage patterns and app access times to anyone with Firestore access | `src/services/activityLog.js` | Encrypt log entries with the master key before writing |
| MED-11 | Device metadata (OS, browser, userAgent) stored plaintext — enables fingerprinting across sessions | `src/services/deviceTracker.js` | Encrypt device metadata object before writing to Firestore |
| MED-12 | Firestore batch writes not chunked — operations on vaults with >500 documents will throw and leave state partially updated | `src/services/vault.js`, `src/services/collaboration.js` | Split batch operations into sequential chunks of ≤500 |
| MED-13 | WebRTC uses public Google STUN servers only — calls fail on symmetric NAT (common on corporate/mobile networks) | `src/apps/secureshare/hooks/useWebRTC.js` | Deploy a self-hosted TURN server (e.g. coturn); add credentials to ICE config |

## Configuration Issues

### `.env` Committed to Git History

- The `.env` file is listed in `.gitignore` but was committed in an earlier commit (`9f894a0`)
- Firebase API keys are designed to be public (security relies on Firestore/Storage rules, not key secrecy), but exposing them in Git history is poor hygiene
- **Fix:** Run `git-filter-repo` or BFG Repo Cleaner to purge from history. Consider using Firebase Hosting environment config or CI/CD secrets instead of a committed `.env`

### Vite Dev Server

- `vite.config.js`: `host: true` binds the dev server to all network interfaces (`0.0.0.0`)
- Acceptable for local mobile testing, but verify firewall rules prevent external exposure

### Content Security Policy Notes

- `'unsafe-eval'` is required for Argon2id WebAssembly — acceptable trade-off, document rationale
- `data:` and `blob:` in `script-src` is broad; acceptable given encrypted file handling requirements

**Headers deployed via `firebase.json`:**
- `Content-Security-Policy` — comprehensive
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: SAMEORIGIN`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy: camera=(self), microphone=(self), geolocation=()`

## WebRTC & Media

**File:** `src/apps/secureshare/hooks/useWebRTC.js`

### Signaling Flow

1. User registers presence in RTDB at `presence/{uid}`
2. Caller creates WebRTC offer; encrypts signal with ECDH P-256 (ephemeral) or RSA-4096 fallback
3. Encrypted signal written to RTDB `signals/{recipientUid}`
4. Recipient decrypts signal, creates answer, ICE candidates exchanged
5. `RTCPeerConnection` established; media streams negotiated via `getUserMedia()`
6. Signals auto-deleted after consumption; presence removed on disconnect

### Call State Machine

```
IDLE → CALLING (offer sent) → CONNECTED (answer received) → IDLE (end call)
IDLE → INCOMING (offer received) → CONNECTED (accepted) → IDLE (reject/end)
```

### ICE Configuration

```javascript
iceServers: [
  { urls: 'stun:stun1.l.google.com:19302' },
  { urls: 'stun:stun2.l.google.com:19302' }
]
```

- Public Google STUN only — no TURN server configured (see MED-13)
- Forward secrecy on signaling via ephemeral ECDH key pairs per signal message

## Strengths

1. **Zero-knowledge architecture** — server never sees plaintext data
2. **Argon2id KDF** — memory-hard (64 MB), GPU-resistant (once CRIT-1 is fixed)
3. **ECDH forward secrecy** — per-message ephemeral keys for 1:1 chats
4. **Per-document collaboration keys** — breaching one shared doc does not expose others
5. **URL fragment for public share keys** — decryption key never transmitted to server
6. **Key rotation on collaborator removal** — removed members lose access on next rotation
7. **Auto-lock on inactivity + tab hidden** — minimizes exposure window
8. **PBKDF2 → Argon2id auto-migration** — transparently upgrades legacy users
9. **Device session tracking** — active session management with revocation
10. **Comprehensive security headers** — CSP, X-Frame-Options, Permissions-Policy
11. **Firebase App Check** — ReCAPTCHA v3 bot prevention
12. **rehype-sanitize** — XSS prevention in markdown rendering
