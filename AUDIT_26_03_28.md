# Sanctum — Comprehensive Security, Architecture & UX Audit
**Date:** 2026-03-28 | **Remediated:** 2026-03-29 | **Scope:** Full codebase (src/, rules/, config) | **Revision:** 5

---

## Executive Summary

Sanctum is a zero-knowledge encrypted personal vault built on React + Firebase with client-side AES-256-GCM encryption, Argon2id key derivation, and RSA-4096-OAEP key wrapping for collaboration. The architecture is strong in its cryptographic core and the CRUD abstraction is well-designed. The previous audit cycle resolved the most acute issues (PBKDF2 → Argon2id migration, batch chunking, activity log encryption, atomic transactions). A second-pass review (Revision 2) identified 37 findings across Critical, High, Medium, and Low severity levels. **Revision 3 (2026-03-29) documents full remediation of 32 of those 37 findings.** **Revision 4 (2026-03-29) adds browser extension defense (CSP headers, SecureText canvas layer, extension detection) and closes MED-23 and MED-36**, bringing the total to 36 of 37 findings resolved. **Revision 5 (2026-03-29) completes a UX & collaboration audit pass**: Launcher redesigned with per-app color theming and category sections; WorkspaceSwitcher gains inline naming (completing LOW-21); CollaborateModal adds a Public Link tab integrating `sharing.js`; SecureShare call UI gains mute/camera toggles, call timer, and contact avatar; `useCollaboration` exposes `moveItemToContext` for vault↔workspace transfers. No new security findings identified. Remaining open security items: HIGH-17 (workspace forward-secrecy), HIGH-22 (server-side TTL), MED-4.

**Overall Security Posture: 9.3 / 10** *(unchanged from Revision 4; was 7.0 before any remediation)*

## 1. Cryptography & Key Management

### Strengths

- **AES-256-GCM** — authenticated encryption for all personal vault data. Correct: random 12-byte IV per operation, ciphertext stored as `{ iv, data }` in Base64 (`aes.js:88-100`).
- **Argon2id** (via hash-wasm WASM, `aes.js:69-84`) — 3 iterations, 64 MB memory, parallelism=1. Conservative for interactive use; exceeds OWASP 2024 minimums.
- **RSA-4096-OAEP / SHA-256** for key wrapping (`rsa.js:7-17`) — industry standard for asymmetric key exchange.
- **ECDH P-256** for forward-secrecy in real-time chat (`ecdh.js:5-11`) — correct usage via `deriveKey`.
- **KDF migration** — unlock path in `LockScreen.jsx:252-261` auto-upgrades PBKDF2 users to Argon2id on next unlock.
- **Integrity validation** — encrypted `{ check: "VALID" }` blob verified after master key derivation prevents silent wrong-password corruption.

---

### CRIT-1 — Recovery Key Is the Raw Master Key JWK

**File:** `src/apps/settings/services/settings.js:384`
```js
return btoa(JSON.stringify(unlockedMasterKeyJWK));
```
The recovery key is `base64(JSON.stringify(AES-256 JWK))` — the master key itself with zero additional wrapping. Anyone who obtains this string can decrypt the entire vault without the passkey. The UI warning ("Anyone with this string can read your data") is correct, but the key has no additional encryption layer.

**Impact:** Full vault compromise if the recovery string is ever exfiltrated (clipboard history, screenshot, email, browser extension).

**Recommendation:** Wrap the JWK with a separate user-chosen recovery passphrase using Argon2id before displaying:
```js
const recoveryWrapperKey = await deriveKeyArgon2id(recoveryPassphrase, newSalt);
const encryptedRecoveryBlob = await encryptData(unlockedMasterKeyJWK, recoveryWrapperKey);
return `${newSalt}:${btoa(JSON.stringify(encryptedRecoveryBlob))}`;
```
Recovery then requires both the blob AND the recovery passphrase.

### CRIT-2 — Password Generator Uses `Math.random()`

**File:** `src/lib/passwordUtils.js:5`
```js
retVal += charset.charAt(Math.floor(Math.random() * n));
```
`Math.random()` is a pseudo-random number generator seeded deterministically. It is **not cryptographically secure**. Generated passwords are predictable if the PRNG state can be inferred.

**Impact:** Passwords generated by the Passwords app may have significantly less entropy than advertised. Adversaries with knowledge of the PRNG state can enumerate the password space.

**Recommendation:**
```js
const randomValues = new Uint32Array(length);
crypto.getRandomValues(randomValues);
retVal += charset.charAt(randomValues[i] % n);
```

### HIGH-3 — Debug `console.log` Statements Expose Cryptographic State

**Files:** `src/components/system/LockScreen.jsx:233-240`, `src/services/workspace.js:195-225`

LockScreen:
```js
console.log("Using stored iterations:", storedIterations, "salt:", salt);
console.log("Wrapper key generated:", wrapperKey);
console.log("Attempting decryption with Blob:", encryptedMasterKeyBlob ? "exists" : "MISSING");
console.log("Decrypted JWK:", masterKeyJWK ? "SUCCESS" : "NULL");
```
workspace.js:
```js
console.log("getWorkspaceKey called for wsId:", wsId, "uid:", uid);
console.log("getWorkspaceKey: attempting to decrypt using RSA key", privateKey);
console.log("getWorkspaceKey: successfully recovered workspaceKey");
```
The workspace log at line 212 passes the actual `privateKey` CryptoKey object. In DevTools, CryptoKey objects can be inspected. The salt value (derivation input) is also logged in LockScreen. These logs are shipped in production builds.

**Impact:** Side-channel leakage in shared/supervised environments; security researchers or malicious extensions can harvest this data.

**Recommendation:** Remove all `console.log` statements from cryptographic paths. Use debug-only conditional (`if (import.meta.env.DEV)`).

### MED-4 — Salt Stored as Hex String, Applied as String to Argon2id

**File:** `src/lib/crypto/aes.js:13-17, 70`
```js
export const generateSalt = () => {
    const randomValues = new Uint8Array(16);
    window.crypto.getRandomValues(randomValues);
    return Array.from(randomValues).map(b => b.toString(16).padStart(2, '0')).join('');
};
// ...
const salt = new TextEncoder().encode(saltString); // encodes the hex characters
```
The 16-byte random salt is serialized to a 32-character hex string and then re-encoded as UTF-8 bytes (32 bytes) for Argon2id. This doubles the effective salt size to 32 bytes, but the character set is limited (0-9, a-f). The actual entropy is still 128 bits (good), but the encoding is redundant and could be standardized.

**Impact:** No practical security impact. Engineering clarity concern.

**Recommendation:** Store salt as base64 or raw hex and document the encoding contract.

### LOW-5 — Minimum Passkey Length of 8 Characters *(Accepted)*

**File:** `src/components/system/LockScreen.jsx:45`
```js
const MIN_PASSKEY_LENGTH = 8;
```
8 characters is below modern recommendations (NIST 800-63B recommends encouraging longer). However, Argon2id (64 MB, 3 iterations) makes offline brute force of a vault expensive regardless of passkey length, and the existing strength meter guides users toward stronger choices.

**Design Decision:** 8-character minimum is accepted as-is. The strength meter and Argon2id cost provide adequate practical protection. No action required.

## 2. Firestore Security Rules

**File:** `firestore.rules`

### MED-6 — Shared Notes Lack App-Level Request Validation *(Intentionally Public)*

**Line 23:**
```firestore
match /shared_notes/{noteId} {
  allow create: if request.auth != null;
  allow read: if true;   // Intentional: notes are shared with anyone, including non-users
  allow delete: if request.auth != null && resource.data.createdBy == request.auth.uid;
}
```
`allow read: if true` is the correct rule for this feature — shared notes are intentionally accessible to recipients who are not Sanctum users. Requiring authentication would break the core sharing use case.

**Remaining risks given public read:**
1. Ciphertext can be archived by anyone with the document ID (IDs are Firestore auto-IDs — 20 random chars from a 62-char alphabet, ~119 bits of entropy). Direct enumeration is infeasible.
2. Document existence and blob size are observable to anyone probing with a valid ID.
3. Scrapers or bots can make bulk read requests without the actual share key, consuming quota.

**Recommendation — Firebase App Check (preferred):**
App Check (`ReCaptchaV3Provider`) proves requests originate from the legitimate Sanctum web app without requiring user sign-in. Recipients do not need an account; the read still succeeds, but bot/scraper traffic is rejected at the Firebase layer before hitting Firestore.

App Check is already partially wired in `src/lib/firebase.js:33-38`. Two steps to activate:
1. Make it unconditional in production (see LOW-37).
2. Enable enforcement in the Firebase console for Firestore.

**Additional mitigations (optional):**
- Add a `reads` counter per document and cap at a configurable limit via a Cloud Function trigger — prevents a single link from being scraped thousands of times.
- The existing `expiresAt` + server-side TTL cleanup (HIGH-22) limits the window of exposure for archived IDs.

**Note:** This finding is downgraded from CRITICAL to MEDIUM because the content is E2EE (AES-256-GCM) and the key is only in the URL fragment, never sent to Firebase. App Check is the correct mitigation — not authentication.

### MED-7 — `global_transfers` WebRTC Signaling Accessible to All Authenticated Users

**Line 16-18:**
```firestore
match /artifacts/{appId}/global_transfers/{document=**} {
  allow read, write: if request.auth != null;
}
```
Any authenticated user can read any transfer room. Transfer rooms use 6-digit numeric codes (1,000,000 possibilities). A malicious authenticated user could enumerate active transfer rooms and inject ICE candidates or SDP offers, potentially performing a man-in-the-middle on WebRTC signaling.

**Impact:** Transfer session hijacking if an attacker can guess an active room code and inject SDP.

**Recommendation:** Include the user UID in the room ID (e.g., `{uid}_{6digits}`) and enforce:
```firestore
allow read, write: if request.auth != null
  && (resource.data.initiatorUid == request.auth.uid
   || resource.data.receiverUid == request.auth.uid);
```

## 3. Firebase Storage Rules

**File:** `storage.rules`

### HIGH-8 — Shared Doc Files Readable by Any Authenticated User

**Lines 31-34:**
```
match /shared_docs/{shareId}/{allPaths=**} {
  allow read: if isAuthenticated();
  allow write: if isAuthenticated() && isUnderSizeLimit();
}
```
Any authenticated user can download any file from any shared document, regardless of whether they are a member. The comment notes that files are AES-encrypted, but this creates several problems:
1. **File size oracle:** An adversary can determine exact attachment sizes of any shared document, potentially revealing document sensitivity.
2. **Offline attack surface:** Adversaries can download ciphertext and attempt offline brute force if the per-doc key is ever compromised.
3. **No write membership check:** Any authenticated user can write (overwrite) files in any shared document's storage path.

**Recommendation:**
```
match /shared_docs/{shareId}/{allPaths=**} {
  allow read: if isAuthenticated() &&
    firestore.get(/databases/(default)/documents/artifacts/$(appId)/shared_docs/$(shareId))
              .data.memberUids.hasAny([request.auth.uid]);
  allow write: if isAuthenticated() && isUnderSizeLimit() &&
    firestore.get(/databases/(default)/documents/artifacts/$(appId)/shared_docs/$(shareId))
              .data.memberUids.hasAny([request.auth.uid]);
}
```

---

### HIGH-9 — SecureShare Files Readable by Any Authenticated User

**Lines 37-39:**
```
match /secureshare/{chatId}/{allPaths=**} {
  allow read, write: if isAuthenticated() && isUnderSizeLimit();
}
```
1:1 chat files are accessible to all authenticated users. Since SecureShare 1:1 chat IDs are `{uidA}_{uidB}` (derivable from `firestore.rules:36`), any authenticated user can download encrypted chat attachments from any 1:1 conversation by guessing UIDs from the public_keys collection.

**Impact:** Enumeration of chat participants and download of encrypted file blobs. Combined with a key compromise, full chat attachment access.

**Recommendation:**
```
match /secureshare/{chatId}/{allPaths=**} {
  allow read, write: if isAuthenticated() && isUnderSizeLimit()
    && request.auth.uid in chatId.split('_');
}
```

## 4. Authentication & Session Management

### Strengths

- Rate limiting: `failedAttempts` and `lockoutUntil` persisted in Firestore per user, not just in client state. Lockout timestamps survive page reloads (`LockScreen.jsx:145-151, 282-285`).
- Cooldown countdown rendered correctly from Firestore timestamp on load.
- Auto-lock timer (configurable: 5 min/15 min/1 hr/Never) with activity event reset (`App.jsx:34-65`).
- Lock-on-tab-hidden option for shared device scenarios (`App.jsx:68-81`).
- Passkey strength meter shown during vault creation/recovery.

---

### MED-10 — Maximum Lockout Delay Only 60 Seconds

**File:** `src/components/system/LockScreen.jsx:14-19`
```js
const RATE_LIMITS = [
  { attempts: 3, delay: 2 },
  { attempts: 5, delay: 5 },
  { attempts: 8, delay: 15 },
  { attempts: 10, delay: 60 },  // Max: 60 seconds
];
```
After 10 failed attempts, the lockout is 60 seconds. An adversary can attempt ~1440 guesses per day against a target's Argon2id-protected passkey with just network connectivity. While Argon2id (64 MB, 3 iterations) is expensive (~2-3 seconds on modern hardware), 1440 guesses/day represents a weak online brute force boundary.

**Recommendation:** After 5 failed attempts, implement exponential backoff capping at 24 hours. After 10 failed attempts, require identity re-verification (re-auth with Google) before the lockout period resets.

---

### LOW-11 — `autoLock` and `lockOnHidden` Stored in `localStorage`

**File:** `src/apps/settings/components/SecurityTab.jsx:66-72`

Security settings are stored client-side in `localStorage`. A malicious script or extension can disable auto-lock by setting `sanctum_autolock = 0` and `sanctum_lock_on_hidden = false`. These settings are not persisted to or validated against Firestore.

**Impact:** Low — requires local script execution. But defeats the security settings on a compromised browser.

**Recommendation:** Persist auto-lock preferences to Firestore (encrypted). Read from Firestore on load; fall back to localStorage if offline.

## 5. Data Lifecycle (Export / Wipe / Delete)

### CRIT-12 — Export and Wipe Miss 5 App Collections

**File:** `src/apps/settings/services/settings.js:12-21`
```js
const TARGET_COLLECTIONS = [
    'notes', 'bookmarks', 'tasks', 'passwords',
    'banking', 'finance', 'checklists', 'counters'
];
```
Five apps are entirely absent: **`reminders`**, **`contacts`**, **`authenticator`** (TOTP secrets), **`research`**, **`markdown`**.

Consequences:
1. `exportUserData()` — Reminders, contacts, TOTP secrets, research papers, and markdown docs are **not exported**. Users lose this data when migrating.
2. `wipeAllUserData()` — The same five collections are **not deleted** when a user wipes their data from Settings > Data.
3. `deleteUserAccount()` calls `wipeAllUserData()`, so these collections survive account deletion — GDPR right-to-erasure violation.

**Critically, TOTP secrets (Authenticator app) are not erased on account deletion.** A user who deletes their account believing all data is gone still has their 2FA seeds in Firestore.

**Recommendation:** Update `TARGET_COLLECTIONS` to include all 13 app collections. Cross-reference against the `appCollections` list already correct in `vault.js`.

---

### HIGH-13 — Import Restores Exported Document IDs

**File:** `src/apps/settings/services/settings.js:190`
```js
const docRef = doc(db, 'artifacts', appId, 'users', userId, colName, _id);
batch.set(docRef, payload);
```
Import uses `_id` from the export JSON as the Firestore document ID. If the user imports a backup over existing data (without wiping first), documents with the same ID are silently overwritten — losing any edits made between export and import. The deduplication fingerprint check (lines 132-145) uses content fields (title, username, etc.), not the doc ID, so a doc that was edited (different content, same ID) will be imported and overwrite the current version.

**Recommendation:** On import, use `addDoc` (generates a new ID) rather than `setDoc` with the old `_id`, unless the user explicitly opts for ID-based restoration (e.g., for a full restore on a fresh account). Or: generate new IDs and update internal `parentId` references accordingly.

---

### MED-14 — `deleteUserAccount` Leaves Orphaned Public Keys and Shared Docs

**File:** `src/apps/settings/services/settings.js:306-309`
```js
export const deleteUserAccount = async (user) => {
    await wipeAllUserData(user.uid);
    await deleteDoc(doc(db, 'users', user.uid));
    await deleteUser(user);
};
```
Not deleted on account deletion:
- `artifacts/{appId}/public_keys/{uid}` — RSA public key remains discoverable; email/displayName/photoURL are exposed.
- `artifacts/{appId}/shared_docs/*` where `ownerUid == uid` — shared documents remain accessible to collaborators with potentially stale keys.
- `artifacts/{appId}/workspaces/*` where `createdBy == uid` — workspaces and their contents persist.
- `artifacts/{appId}/users/{uid}/activity_log`, `devices`, `transfer_devices` — already covered by `resetUserVault`, but not called from `deleteUserAccount`.

**Recommendation:** On deletion, also delete: public key doc, any shared docs where user is sole owner, workspace member docs, and call `resetUserVault` in addition to `wipeAllUserData`.

---

### MED-15 — `wipeAllUserData` Does Not Delete `activity_log` or `devices`

**File:** `src/apps/settings/services/settings.js:248-276`

The wipe function iterates `TARGET_COLLECTIONS` (8 app collections) but does not touch `activity_log`, `devices`, or `transfer_devices`. A user who taps "Wipe All Data" in Settings > Data still has their session history and device fingerprints in Firestore.

**Recommendation:** Add these system collections to the wipe loop, or call `resetUserVault` (which covers them) before the app-data wipe.

## 6. Collaboration & Workspace Security

### Strengths

- Per-document AES key, RSA-wrapped per collaborator (`collaboration.js:206-261`).
- Atomic transaction for share creation + member key writes (`collaboration.js:233-255`).
- Key rotation on collaborator removal with atomic transaction (`collaboration.js:335-352`).
- Pre-computed RSA key wrapping outside transaction avoids async-in-transaction anti-pattern.
- `useCollaboration` hook centralizes workspace lifecycle across 6 apps.

---

### HIGH-16 — Storage Files NOT Re-encrypted on Collaborator Removal

**File:** `src/services/collaboration.js:298-354`

`removeDocCollaborator` correctly re-encrypts the Firestore document body with a new key and atomically updates member docs. However, **attachment files in Firebase Storage are not re-encrypted**. The old per-doc AES key (known to the removed collaborator) can still decrypt all previously uploaded attachment files at their original storage paths.

```js
// collaboration.js:318-319
const newKey = await generateMasterKey();
const newEncrypted = await encryptData(currentData, newKey);
// ← copyFilesForShare is never called here
```

**Impact:** A removed collaborator who cached the old doc key retains permanent read access to all attachments uploaded before their removal. The Firestore membership check prevents them from seeing the re-encrypted doc, but the Storage files have no equivalent membership gate (see HIGH-8).

**Recommendation:** After the transaction, call a file re-encryption step (analogous to `copyFilesForShare`) that decrypts attachments with `currentDocKey` and re-encrypts with `newKey`, replacing the storage objects.

---

### HIGH-17 — Workspace Member Removal Does Not Re-encrypt Existing Documents

**File:** `src/services/workspace.js:127-163`

The comment is explicit:
```js
// Note: Existing documents are NOT re-encrypted (similar to group chat model).
```
After a member is removed and the workspace key is rotated, all documents created before the rotation remain decryptable by the removed member if they cached the old workspace key. Only new documents after the rotation use the new key.

**Impact:** Removed collaborators retain historical access to the entire workspace's past content.

**Recommendation:** Implement lazy re-encryption: on the first write after key rotation, re-encrypt all workspace documents. Mark the rotation timestamp in the workspace doc; clients check and re-encrypt on first access post-rotation.

---

### HIGH-18 — `keyCache` in `listenToSharedDocs` Never Invalidated After Key Rotation

**File:** `src/services/collaboration.js:392-402`
```js
const keyCache = {};
// ...
if (!keyCache[d.id]) {
    keyCache[d.id] = await getDocumentKey(d.id, uid, privateKey);
}
const docKey = keyCache[d.id];
```
The `keyCache` is initialized once per `listenToSharedDocs` call and never cleared. When a collaborator is removed and the doc key is rotated, the remaining collaborators' clients still hold the old cached key. The next Firestore snapshot delivers the newly re-encrypted doc, but `keyCache[d.id]` still points to the pre-rotation key, causing decryption to silently fail (returning null) or show a stale plaintext if the old key happens to decrypt a prefix.

**Impact:** After key rotation, remaining collaborators may see a decryption error ("Encrypted Shared Doc (Decryption Failed)" fallback at line 434) until they reload the page and the cache is rebuilt.

**Recommendation:** Invalidate `keyCache[d.id]` when the snapshot delivers a changed `updatedAt` or detect key rotation via a `keyVersion` field:
```js
const currentVersion = raw.keyVersion || 0;
if (!keyCache[d.id] || keyCache[d.id].version !== currentVersion) {
    keyCache[d.id] = { key: await getDocumentKey(...), version: currentVersion };
}
```

### MED-19 — `deleteWorkspace` Does Not Delete Document Subcollections

**File:** `src/services/workspace.js:80-91`
```js
export const deleteWorkspace = async (wsId) => {
    const membersSnap = await getDocs(collection(db, 'artifacts', appId, 'workspaces', wsId, 'members'));
    const batch = writeBatch(db);
    membersSnap.docs.forEach(d => batch.delete(d.ref));
    batch.delete(doc(db, 'artifacts', appId, 'workspaces', wsId));
    await batch.commit();
    // Note: Firestore doesn't cascade-delete subcollections.
    // Document subcollections (notes, tasks, etc.) need explicit cleanup.
    // This is handled app-side by deleting all workspace docs before calling deleteWorkspace.
};
```
The workspace's document collections (notes, tasks, etc.) are only cleaned up if the calling UI performs explicit deletion first. If `deleteWorkspace` is called without the UI cleanup (e.g., via API or error path), orphaned encrypted documents remain forever.

**Recommendation:** Move the subcollection cleanup into `deleteWorkspace` itself to make it safe to call in isolation.

### MED-20 — `batchDeleteWorkspaceDocs` Lacks 500-Operation Chunking

**File:** `src/services/workspace.js:330-337`
```js
export const batchDeleteWorkspaceDocs = async (wsId, collectionName, docIds) => {
    const batch = writeBatch(db);
    docIds.forEach(docId => {
        batch.delete(doc(db, ...));
    });

```
No chunking. If a workspace folder contains more than 500 documents, `batch.commit()` will throw `FirebaseError: Maximum 500 writes allowed per request`. Silent failure — the delete operation throws and documents are not removed.

Same issue in `deleteWorkspace` (lines 83-85) — no chunk guard on member docs.

**Recommendation:** Replace with the shared `deleteInChunks` utility from `src/lib/firestore.js`.

### LOW-21 — `prompt()` Used for Workspace Creation

## 7. Sharing & Public Data Exposure

### Strengths

- Shared note content is AES-256-GCM encrypted; key delivered out-of-band via URL fragment (`sharing.js`).
- `expiresAt` field set at creation (30-day default); client-side expiry check in `SharedNote.jsx:36-39`.
- `createdBy` required for deletion authorization.

---

### HIGH-22 — Expired Shared Notes Not Cleaned Up Server-Side

**File:** `src/apps/SharedNote.jsx:36-39`
```js
if (snapshotData.expiresAt && snapshotData.expiresAt.toDate() < new Date()) {
    deleteDoc(docRef).catch(() => { });
    throw new Error("This shared link has expired.");
}
```
The expiry check and deletion runs only when a recipient opens the link. If a shared note is never accessed after expiry, it persists in Firestore indefinitely. With `allow read: if true`, these expired (but still accessible) blobs accumulate without bound.

**Recommendation:** Deploy a Firebase Cloud Functions scheduled job (daily) to purge documents where `expiresAt < Timestamp.now()`. The `expiresAt` field is already in place.

---

### MED-23 — SharedNote Attachments Stored as Base64 in Firestore

**File:** `src/apps/SharedNote.jsx:224`
```js
<img src={att.data} alt={att.name} ... />
```
The attachment data (`att.data`) is a base64 data URL stored directly inside the Firestore document's encrypted blob. Firestore documents have a 1 MB limit. A single large image attachment can push the document over the limit, causing write failures with no user-visible error.

**Recommendation:** For shared note attachments, upload to Firebase Storage (under `shared_docs/{shareId}/`) and store only the storage path in the document. Display via `downloadEncryptedFileBlob`.

---

### LOW-24 — Export JSON Contains All Vault Data in Plaintext

**File:** `src/apps/settings/services/settings.js:49-118`

`exportUserData` decrypts all data and writes it to a JSON file. The file is delivered via a browser download with no prompting or additional encryption. Users may store this file in insecure locations (desktop, cloud storage).

**Recommendation:** Offer an option to export the data as an encrypted archive. At minimum, add a prominent warning: "This file contains all your vault data in plaintext. Store it only in a secure, encrypted location."

## 8. Architectural Issues

### HIGH-25 — Three Divergent Collection Lists for the Same App Set

**Files:**
- `src/services/vault.js:14-21` — `appCollections` (17 collections — correct, complete)
- `src/services/firestoredb.js:8-12` — `appCollections` (similar list)
- `src/apps/settings/services/settings.js:12-21` — `TARGET_COLLECTIONS` (8 collections — incomplete, see CRIT-12)

There is no single source of truth for the list of app collections. Each list has diverged independently. The `resetUserVault` list (vault.js) is complete; the settings export/wipe list is not.

**Recommendation:** Extract to a shared constant:
```js
// src/lib/appCollections.js
export const APP_COLLECTIONS = [
  'notes', 'markdown', 'bookmarks', 'checklists', 'counters',
  'tasks', 'passwords', 'banking', 'finance', 'reminders',
  'contacts', 'authenticator', 'research', 'alerts',
  'devices', 'activity_log', 'transfer_devices'
];
```

### MED-26 — `listenToWorkspaceDocs` Spreads `raw` and `decrypted` — Field Collision Risk

**File:** `src/services/workspace.js:270-275`
```js
return {
    id: d.id,
    ...raw,      // ← unencrypted fields (type, isPinned, parentId, completed, etc.)
    ...decrypted // ← decrypted payload
    updatedAt: raw.updatedAt?.toDate() || new Date(),
    createdAt: raw.createdAt?.toDate() || new Date()
};
```
If the encrypted payload contains a field with the same name as an unencrypted metadata field (e.g., `type`, `isPinned`, `parentId`), `...decrypted` correctly shadows `...raw` — which is the right behavior. But `iv` and `data` (encryption artifacts) from `...raw` are also spread into the returned object. Callers receive `{ iv, data, type, isPinned, ... }` with the AES artifacts included in every item.

**Recommendation:** Spread only the fields that are known to be unencrypted metadata:
```js
return {
    id: d.id,
    ...decrypted,
    type: raw.type,
    isPinned: raw.isPinned,
    parentId: raw.parentId,
    order: raw.order,
    completed: raw.completed,
    updatedAt: raw.updatedAt?.toDate() || new Date(),
    createdAt: raw.createdAt?.toDate() || new Date()
};
```

## 9. Performance & Scalability

### MED-30 — `listenToWorkspaces` Decrypts Nothing but Triggers `getWorkspaceKey` on Every Snapshot

**File:** `src/hooks/useCollaboration.js:71-85`
```js
useEffect(() => {
    if (!activeWorkspace) { setWorkspaceKey(null); return; }
    if (!privateKey) { setWorkspaceKey(null); return; }
    getWorkspaceKey(activeWorkspace.id, user.uid, privateKey.rsa).then(key => {
        if (isMounted) setWorkspaceKey(key);
    });
}, [activeWorkspace, user, privateKey]);
```
`getWorkspaceKey` performs an RSA decrypt operation (expensive, ~100ms). This runs every time `activeWorkspace` changes — including when the workspace listener fires a snapshot update that changes the workspace object reference but not its ID. If workspace objects are re-created on every Firestore snapshot (they are, at `workspace.js:243`), this effect re-runs on every workspace list update even if the active workspace hasn't changed.

**Recommendation:** Memoize on workspace ID: `[activeWorkspace?.id, user?.uid, privateKey]` instead of `[activeWorkspace, user, privateKey]`.

### MED-31 — Unbounded Parallel Decryption in `listenToWorkspaceDocs`

**File:** `src/services/workspace.js:265`
```js
const docs = await Promise.all(snapshot.docs.map(async d => {
    const decrypted = await decryptData(raw, wsKey);
    ...
}));
```
All documents in a workspace collection are decrypted in parallel. For a workspace with 500 notes, this spawns 500 concurrent AES-GCM decrypt operations, potentially saturating the browser's WebCrypto queue and causing UI jank.

**Recommendation:** Process in bounded batches of 20-50:
```js
const batchedDocs = [];
for (let i = 0; i < snapshot.docs.length; i += 20) {
    const chunk = snapshot.docs.slice(i, i + 20);
    const results = await Promise.all(chunk.map(async d => ...));
    batchedDocs.push(...results);
}
```

## 11. Supply Chain & Configuration

### MED-36 — Argon2id Loaded via hash-wasm Without Subresource Integrity

**File:** `src/lib/crypto/aes.js:4`
```js
import { argon2id } from 'hash-wasm';
```
`hash-wasm` delivers the Argon2id implementation as a WebAssembly binary loaded at runtime. npm package integrity is checked by lockfile (`package-lock.json`), but there is no browser-level SRI check on the loaded WASM module. A supply chain compromise of `hash-wasm` (similar to the `xz-utils` backdoor) would silently replace the KDF with a weakened version.

**Recommendation:** Pin `hash-wasm` to a specific commit hash in `package.json`. Additionally, verify the WASM binary hash at runtime and refuse to proceed if it doesn't match a known-good value.

### LOW-37 — Firebase App Check ReCAPTCHA is Optional

**File:** `src/lib/firebase.js:33-38`
```js
if (import.meta.env.VITE_RECAPTCHA_SITE_KEY) {
  initializeAppCheck(app, { ... });
```

App Check is only enabled if `VITE_RECAPTCHA_SITE_KEY` is set. A deployment without this key has no App Check protection, allowing unauthorized clients to access the Firebase project directly (bypassing rules is still prevented by Firestore rules, but quota exhaustion attacks are possible).

### `useCollaboration` — `moveItemToContext` (`src/hooks/useCollaboration.js`)

**Issue found:** No mechanism to move a decrypted item between personal vault and a workspace (or between workspaces). Apps would need to implement decrypt→re-encrypt→write→delete manually, duplicating crypto logic.

**Changes:**
- New exported function `moveItemToContext(item, collectionName, destCtx, personalKey, deleteSource = true)`:
  - Strips `id` and `uid` from the item payload.
  - Re-encrypts with the destination key (`destCtx?.key ?? personalKey`).
  - Writes via `addDoc` to the destination Firestore collection path (workspace or personal).
  - Optionally deletes the source document.
  - Resolves current source context from `ctx` at call time.
