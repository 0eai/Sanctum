# Collaboration & Sharing Audit — 2026-03-29

> Full audit of workspace, per-document collaboration, and public-link sharing
> across all six collaboration-enabled apps: **notes, markdown, tasks, checklist,
> research, bookmarks**.

---

## Executive Summary

All 10 bugs identified in this audit have been fixed as of 2026-03-29. The collaboration
system is now functional: the collaborators list loads correctly, viewer/editor permissions
are enforced both client-side and in Firestore rules, each app has a single unified share
entry point via `CollaborateModal`, and the public-link tab correctly reads and persists
link state.

## Detailed Bug Descriptions

---

### COLLAB-1 🔴 — Dual share dialogs and duplicate icons

**Files:** `src/apps/notes/Notes.jsx`, `src/apps/tasks/Tasks.jsx` (and all other collab apps)

Every collaboration-enabled app renders **two independent share UIs**:

1. **Old inline `<Modal isOpen={!!shareModal} title="Share Note">` / `title="Share Task">`**
   — a custom public-link-only dialog wired to `handleShare` / `handleShareTask`.
   Triggered by the **Link icon** (`onShare` prop) on NoteCard / NoteEditor / TaskCard / TaskEditor.

2. **New `<CollaborateModal>`** — the central two-tab modal (Collaborators + Public Link).
   Triggered by the **Users icon** (`onCollaborate` prop) on the same components.

Both exist simultaneously. The result is:
- Two share-related icons in the editor toolbar
- Two completely different dialogs for creating a public link
- If a user creates a link in the old dialog and then opens the new one, the new dialog
  shows no link (not wired to the stored state)

**Root cause:** The per-app `shareModal` code was never removed when `CollaborateModal`
was introduced. The `onShare` + `handleShare` / `handleShareTask` code paths are now dead
weight that conflicts with the new system.

### COLLAB-2 🔴 — Wrong `shareId` passed to CollaborateModal (collaborators list always empty)

**Files:** `src/apps/notes/Notes.jsx:405`, `src/apps/tasks/Tasks.jsx:514`

In every app, the `CollaborateModal` is opened with:

```jsx
<CollaborateModal
  shareId={collab.collaborateModalItem.sharedId || null}
  docKey={collab.collaborateModalItem.docKey || null}
  ...
/>
```

The problem: `item.sharedId` is the **public link ID** — a document ID in the
`shared_notes` Firestore collection (created by `shareNote()` / `shareItem()`).

The `CollaborateModal` expects `shareId` to be a **collaboration share ID** — a document
ID in the `shared_docs` collection (created by `shareDocument()`).

When the Collaborators tab opens, it calls `getShareMembers(shareId)`, which reads
`shared_docs/{sharedId}/members`. If the ID belongs to `shared_notes`, the read fails
with `permission-denied`, causing this branch in `CollaborateModal.jsx:82-84`:

```js
if (e?.code === 'permission-denied' || ...) {
    setShareId(null); setDocKey(null); setMembers([]);
}
```

Members list silently clears. The "No collaborators yet" empty state is shown
even if collaborators exist.

There is no field on personal note/task documents that stores the collaboration shareId
— these are two completely separate concepts that were conflated under the name `sharedId`.

### COLLAB-3 🔴 — `isShared` vs `isSharedDoc` flag mismatch

**Files:** `src/services/collaboration.js:465`, `src/apps/notes/Notes.jsx:258,327`,
`src/apps/tasks/Tasks.jsx:320-321`

`listenToSharedDocs` returns documents with `isShared: true` (line 465):

```js
docs.push({
    ...decrypted,
    isShared: true,           // ← what the service sets
    isOwner: raw.ownerUid === uid,
    ...
});
```

Every app checks `isSharedDoc` (not `isShared`) to decide read-only mode
and to hide the share button:

```jsx
// Notes.jsx:258
readOnly={editorState.isSharedDoc && editorState.role === 'viewer'}

// Notes.jsx:327 (NoteCard)
readOnly={item.isSharedDoc && item.role === 'viewer'}

// Notes.jsx:254 (NoteEditor)
onShare={!ctx && !editorState.isSharedDoc ? (...) : null}
```

Since `isSharedDoc` is always `undefined`, all three checks always fail:
- Read-only mode never activates for shared documents
- The share icon always appears, even on docs the user does not own

### COLLAB-4 🔴 — `role` never fetched — viewer restriction never activates

**Files:** `src/services/collaboration.js` (`listenToSharedDocs`)

The user's role (`'owner'` | `'editor'` | `'viewer'`) is stored in the
`shared_docs/{shareId}/members/{uid}` subcollection. `listenToSharedDocs` never reads
this subcollection, so the returned doc objects contain no `role` field.

```js
// collaboration.js — what IS included:
docs.push({
    ...decrypted,
    ownerUid: raw.ownerUid,
    memberUids: raw.memberUids,
    isShared: true,
    isOwner: raw.ownerUid === uid,
    // ← role is NOT here
});
```

Since `item.role` is always `undefined`, the check `item.role === 'viewer'` is
always `false`. Viewer-role collaborators can edit and save documents.

Combined with COLLAB-3, even if `isSharedDoc` were correct, read-only mode would
still never activate because `role` is missing.

### COLLAB-5 🟠 — `onShareCreated` overwrites public-link `sharedId`

**Files:** `src/apps/notes/Notes.jsx:412-415`, `src/apps/tasks/Tasks.jsx:521-524`

When a new collaboration is created inside `CollaborateModal`, the callback is:

```jsx
onShareCreated={async (newShareId) => {
    await handleSaveNote({ ...collab.collaborateModalItem, sharedId: newShareId });
    // Tasks: await saveTask(user.uid, cryptoKey, { ...item, sharedId: newShareId }, ctx)
}}
```

This saves the **collaboration shareId** into the `sharedId` field, which is the
same field used to store the **public link ID** (set by `shareNote()` / `shareItem()`).

Consequences:
- If the note had an active public link, its ID is silently overwritten → public
  link stops working
- On the next `CollaborateModal` open, `item.sharedId` contains the collaboration
  shareId, which is passed as `shareId` to the modal (a different kind of ID, but
  at least this partially "works" for returning users — an accidental semi-fix for COLLAB-2)
- The two concepts need separate fields: `sharedId` (public link) and `collabShareId`
  (per-user collaboration share)

### COLLAB-6 🟠 — Public-link tab always empty

**Files:** All apps that render `<CollaborateModal>`

`CollaborateModal` has two props for the Public Link tab state:
`publicSharedId` and `publicShareUrlKey`. These are never passed from any app:

```jsx
// Notes.jsx — what is actually passed:
<CollaborateModal
    shareId={...}
    docKey={...}
    appType="notes"
    currentUser={user}
    privateKey={privateKey}
    cryptoKey={cryptoKey}
    // publicSharedId ← missing
    // publicShareUrlKey ← missing
    // onPublicLinkCreated ← missing
    // onPublicLinkRevoked ← missing
    onClose={...}
    onShareCreated={...}
    onShareDeleted={...}
/>
```

The `PublicLinkTab` therefore initialises `sharedId = null` every time the modal
opens, and always shows the "Create Public Link" form — even if the doc already has
an active link. Creating a link from this tab does call `onLinkCreated`, but
since the callback is not connected to anything, the created link ID and key are
lost the moment the modal closes.

### COLLAB-7 🟠 — Viewer role not enforced in Firestore rules

**File:** `firestore.rules`

The current rule for shared documents:

```firestore
match /artifacts/{appId}/shared_docs/{shareId} {
  allow read, update: if request.auth.uid in resource.data.memberUids;
  allow delete: if resource.data.ownerUid == request.auth.uid;
}
```

The rule grants `update` to any `memberUids` member regardless of role.
Reading the role from a subcollection inside a rule is not directly supported by
Firestore, so enforcing viewer-only at the rule level requires storing roles in
the main document (e.g., a `viewerUids` array alongside `memberUids`).

### COLLAB-8 🟡 — `saveSharedDoc` makes no role check

**File:** `src/services/collaboration.js:508`

```js
export const saveSharedDoc = async (shareId, docKey, data) => {
    const encrypted = await encryptData(cleanData, docKey);
    await updateDoc(doc(..., 'shared_docs', shareId), {
        ...encrypted,
        updatedAt: serverTimestamp()
    });
    // No role check before writing
};
```

The client does not validate the caller's role before writing. Since COLLAB-7 means
server rules also don't enforce it, viewers can save changes freely.

### COLLAB-9 🟡 — Workspace viewer role is decorative

**Files:** `src/services/workspace.js`, `firestore.rules`

`inviteMember(wsId, uid, wsKey, role)` stores the role in the
`workspaces/{wsId}/members/{uid}` subcollection. But:

1. `listenToWorkspaceDocs` does not fetch the member's role
2. No app checks role before letting a member edit workspace documents
3. Firestore rules for workspace docs allow `read, write` to any `memberUids` member

The "Viewer" option in `WorkspacePanel` is completely non-functional.

---

### COLLAB-10 🟡 — Share icon appears on collaborated docs not owned by the user

**Files:** Notes.jsx, Tasks.jsx (all collab apps)

Because `isSharedDoc` is always `undefined` (COLLAB-3), the condition:

```jsx
onShare={!ctx && !editorState.isSharedDoc ? (...) : null}
```

Always passes `onShare`, showing the public-link share icon even when the user
is a collaborator viewing someone else's document. Clicking it would create a
public link attributed to the wrong owner.

### Detail

**Bookmarks — Move items between folders** 🔴
Bookmarks is the only folder-based app with no way to move an existing item to a different
folder. All other folder apps (Notes, Tasks, Markdown, Research) expose a move modal.
The service layer already accepts `parentId` on `saveBookmarkItem` — only the UI is missing.

**Notes — Export** 🔴
Every other text-based app (Tasks, Markdown, Checklist) has an export handler. Notes only
has `window.print()`. A simple "Export as Markdown" button in the editor would close this gap.

**Bookmarks — Export** 🔴
Bookmarks already imports from Netscape HTML (browser bookmark format). Without export,
the roundtrip is broken: users can import their bookmarks but cannot get them back out.
Exporting to the same Netscape HTML format is the natural companion.

**Research — Export as BibTeX** 🟠
Research already parses pasted BibTeX entries (`handleBibtexAutoFill`). Exporting a paper
back to a `.bib` file is a direct complement and follows the pattern every other
import-capable app has. `formatCitation` is already implemented in the service layer.

**Checklist — Pin lists** 🟠
Notes, Tasks, and Markdown all support pinning items to the top of the list. Frequently
used checklists (e.g. a grocery list, a daily routine) cannot currently be promoted.
Pin is already an encrypted metadata field in the other app services — the pattern is
well established.

**Research — Pin papers** 🟠
Same rationale as Checklist. Important papers have no way to stay visible at the top.

**Bookmarks — Grid / List view toggle** 🟡
Notes and Research both offer a grid/list toggle. For large bookmark collections a compact
list view (URL + favicon + title on one line) would be more scannable than the current
card grid. Lower priority because the existing grid is already functional.

**Tasks — Tags** 🟡
Notes, Markdown, and Research all support tags for cross-cutting classification.
Tasks organises by folder tabs, which partially substitutes, but tags would allow
filtering across folders (e.g. show all tasks tagged `client-A` regardless of folder).
Lower priority because tabs already provide a good organisational structure.
