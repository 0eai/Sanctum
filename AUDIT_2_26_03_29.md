## 1. Auto-Save Audit — All Editors

### Pattern Overview

Five of the six collaboration-capable apps use an identical auto-save strategy:

```
user edits → local state → useDebounce(1000ms) → hash compare → onSave()
```

Hash comparison prevents redundant Firestore writes when the rendered state matches what was last persisted.

### Per-App Breakdown

| App | Auto-save | Debounce | Hash Guard | `isCreatingRef` guard | Issues |
|-----|-----------|----------|------------|----------------------|--------|
| **Notes** | ✅ | 1 s | ✅ | ✅ | None |
| **Markdown** | ✅ | 1 s | ✅ | ✅ | None |
| **Tasks** | ✅ | 1 s | ✅ | ❌ (not needed — always has an ID) | `tags` field missing from hash before current session (now fixed) |
| **Research** | ✅ | 1 s | ✅ | ❌ | See §6 for bugs |
| **Checklist** | ⚠️ item-level | N/A | N/A | N/A | No document editor; every action is an immediate Firestore write. Correct for this UX pattern but means no "unsaved changes" buffer. |
| **Bookmarks** | ⚠️ modal-based | N/A | N/A | N/A | Explicit save button in `AddBookmarkModal`. No implicit save. |
| **Contacts** | Unknown | Unknown | Unknown | Unknown | Not audited |
| **Passwords** | Unknown | Unknown | Unknown | Unknown | Not audited |

### Issues Common Across All Auto-Save Editors

**S1 — No save indicator on first creation**
`saveStatus` is shown as `'Saving...'` / `'Saved'` but only after the first successful round-trip. If a brand-new document loses connectivity before the first save the user gets no feedback and no local draft is stored.

**S2 — `isCreatingRef` guard is not reset on error**
In `NoteEditor` and `MarkdownEditor`, if the initial `onSave` call throws, `isCreatingRef.current` stays `true` and all subsequent saves are silently suppressed until the editor is remounted.

**Fix:** In the `.catch` handler, reset `isCreatingRef.current = false` unconditionally (already done for the no-ID branch in `MarkdownEditor`, but not fully for `NoteEditor`).

**S3 — PDF upload hack in Research uses `setTimeout`**
`PaperEditor` forces a save after a PDF upload with:
```js
setLastSavedHash(null);
setTimeout(() => handleSave(...), 500);
```
If the component unmounts in that 500 ms window the save is lost. Should use a `useEffect` triggered by `driveFileId` change instead.

**S4 — No offline/network-failure indication**
All editors silently swallow save errors (only `console.error`). If Firestore is unreachable, the user sees "Saved" indefinitely. A visible error state with a manual retry button would improve trust.

**S5 — `saveStatus` prop not standardised**
`MarkdownEditor` receives an explicit `saveStatus` string prop ('saving' | 'saved' | 'error') from the parent. `NoteEditor` derives its own display from `isSaving` state. `TaskEditor` and `PaperEditor` maintain their own `isSaving` state internally. No single source-of-truth approach for the pattern.

## 2. Real-Time Collaboration Model

### Current Architecture

All collab-capable apps use **Firestore `onSnapshot` listeners** for real-time delivery combined with **last-write-wins (LWW)** merge semantics. The flow is:

```
User A edits → debounce 1s → encryptData → setDoc/updateDoc
                                              ↓
                           Firestore triggers onSnapshot on all listeners
                                              ↓
                           User B's app decrypts + re-renders
```

### What Works Well

- **Sub-second delivery** after the 1 s debounce — edits from one user appear on the other's screen within ~2 s of the last keystroke.
- **Silent metadata sync** — changes to `sharedId`, `docKey`, and `memberUids` are applied without disturbing the user's in-progress edit.
- **Atomic key operations** — share creation, collaborator add/remove, and key rotation all use `runTransaction`, preventing partial state.

### Critical Gap — No Conflict Resolution

Because `setDoc` / `updateDoc` with a full payload is used (not field-level merges), **two users editing simultaneously will lose one user's work**. The second write to Firestore always wins, and there is no tombstone or merge record.

This is acceptable for small teams where users rarely edit the same document concurrently, but should be documented as a known limitation and ideally surfaced to the user.

### Recommended Improvements

| ID | Recommendation | Effort |
|----|---------------|--------|
| C1 | **Add edit presence indicators** — when a user opens an editor, write their `uid` + timestamp to a lightweight Firestore `presence/{docId}/{uid}` subcollection (TTL'd via Firebase Functions). Display avatars of current editors in the header. | Medium |
| C2 | **Field-level `updateDoc`** — for text content, use `updateDoc({ encryptedContent: ... })` rather than `setDoc` on the full payload. This narrows the collision window from the whole document to a single encrypted field. | Low |
| C3 | **Stale-document warning** — before saving, compare the local `lastSavedHash` against a Firestore `versionId` counter. If they diverge, warn the user rather than silently overwriting. | Low |
| C4 | **CRDT-based concurrent editing (long-term)** — integrate Y.js with a Firestore CRDT provider for true concurrent editing. This is a significant architectural change, best done as a separate workstream. | Very High |

## 3. Vault ↔ Workspace File Movement

### Current State

`useCollaboration.js` exposes a `moveItemToContext()` function (lines ~155–183) that:

1. Re-encrypts the item payload with the destination key
2. Writes the new document to the destination Firestore collection
3. Optionally deletes the source document

**This function is never called from any app UI.** No app exposes a "Move to workspace" or "Move to personal vault" control.

### Bugs in the Existing Implementation

**M1 — User ID resolution is broken**
```js
const destCol = destCtx?.workspaceId
    ? collection(db, 'artifacts', appId, 'workspaces', destCtx.workspaceId, collectionName)
    : collection(db, 'artifacts', appId, 'users', item.uid ?? item.createdBy ?? '', collectionName);
```
Items in the app state do not carry a `uid` or `createdBy` field — those are not part of the encrypted payload or the public Firestore meta. This path always resolves to `.../users//collectionName`, which will write to an empty string user ID and fail silently (Firestore rules will reject it).

**Fix:** Pass `user.uid` explicitly as a parameter to `moveItemToContext`.

**M2 — Attachments are not moved**
The function only moves the Firestore document record. For Notes, Markdown, and Research, attached files are stored at a path scoped to the source context (e.g., `users/{uid}/notes/{fileId}`). After the document is moved, the new document points to files the destination context cannot access (wrong encryption key, wrong storage path).

**M3 — Folder moves are not recursive**
Calling `moveItemToContext` on a folder moves only the folder document, leaving all child documents orphaned at the source.

**M4 — No progress feedback**
A folder with hundreds of child documents could take 30+ seconds; with no feedback the user cannot tell if the operation is in progress or stalled.

### Recommended Implementation Plan

#### Option A — Client-Side (for documents without file attachments)

1. Fix `moveItemToContext` (pass `userId`, fix the collection path)
2. Add folder recursion (BFS traversal, batch-move children first, then folder)
3. Add "Move to..." button in each app's item context menu / detail view
4. Show a modal with workspace picker + personal vault option
5. Show a spinner + item count during move

#### Option B — Firebase Cloud Function (recommended for items with attachments)

A `moveDocumentToContext` Firebase Function receives:
- `sourceContext`: `{ userId }` or `{ workspaceId }`
- `destContext`: `{ userId }` or `{ workspaceId }`
- `collection`: e.g., `'notes'`
- `docId`: document to move (recursive for folders)
- The caller sends the **decrypted payload** + re-encrypted version (client handles the crypto, function handles storage)

Benefits:
- Runs outside browser memory/timeout limits
- Can move Storage files atomically alongside Firestore documents
- Provides a single status endpoint to poll

#### Storage File Re-encryption

When moving a document that has attachments:

```
Client:
  1. Decrypt file from source storage path (source key)
  2. Re-encrypt with destination key
  3. Upload to destination storage path
  4. Include new storage paths in the destination Firestore doc
  5. Delete source file (or do so in Firebase Function)
```

This must happen **before** the Firestore document is written (to avoid a window where the document references a non-existent file).

#### Minimum Viable UI

Add a "Move to..." option to:
- `ViewBookmarkModal` action row
- Research `PaperCard` action buttons
- Notes/Markdown card hover actions
- Tasks card / editor header

Show a `MoveToContextModal` (similar in shape to the existing `MoveModal` in Bookmarks) with two sections:
- **Personal Vault** (always available)
- **Workspaces** (list from `collab.workspaces`)

## 4. Shared With You — UX Audit & Recommendations

### Current State

`SharedDocsView` is rendered inline at the top of each app's list view when `sharedDocs.length > 0` and the user is not in a workspace.

**Issues:**

**U1 — Dead grouping code**
The component computes `grouped` (by `ownerUid`) but then discards it and renders a flat `sharedDocs.map(...)`. The grouping was clearly intended but never wired up.

**U2 ✅ — Per-app fragmentation resolved with Global Shared Hub**
`src/apps/shared/SharedHub.jsx` was built and registered. It uses a new `listenToAllSharedDocs` listener (no `appType` filter) to show all shared documents in one place. Items are grouped by app type with filter pills, role badges, and deep-link navigation to the correct app. The hub appears in the Launcher under Communication as "Shared" (indigo, `Share2` icon).

**U3 — No role indicator in list**
The role ('editor' / 'viewer') is fetched when a document is opened but not shown in the SharedDocsView card. A user can't tell at a glance whether they can edit a document.

**U4 — No sorting or filtering**
Shared docs are returned in Firestore `createdAt` order with no way to filter by owner, app type, role, or recency.

**U5 — Hidden in workspace mode**
`sharedDocs` are not fetched when `activeWorkspace` is set (by design, to avoid mixing contexts), but there is no indication to the user that shared items exist. Switching away from a workspace to see them is non-obvious.

**U6 — No share notifications**
Users are not notified when a new document is shared with them. Discovery requires visiting each app manually.

### Recommendations

#### Option A — Per-App "Shared" Tab (Lower Effort)

Replace the current inline `SharedDocsView` header block with a dedicated **"Shared"** tab in each app's navigation. This:
- Gives shared documents equal visual weight to personal documents
- Allows role badges, owner avatars, and sort controls to fit naturally
- Is consistent with how Google Drive, Notion, and Figma handle per-app sharing

Implementation sketch:
```jsx
// In app navigation tabs:
['My Notes', 'Shared', 'Pinned']
// 'Shared' tab renders SharedDocsView with grouping enabled
```

Fixes U1 (enable grouping), U3 (add role badge), U4 (add sort options).

#### Option B — Global "Shared with Me" Hub (Better UX, More Effort)

Add a top-level "Shared" section in the main app launcher / dashboard. It shows all documents shared with the user across all apps in one place, grouped by app type or by owner.

This is closer to the experience users expect from Google Workspace / Notion. It requires:
- A cross-app shared-doc listener (or a denormalized `shared_inbox/{uid}` Firestore collection)
- A unified viewer that routes to the correct app on open

**Recommended grouping structure for Option B:**
```
Shared with Me
├── From Alice (3)

│   ├── 📋 Q2 Checklist         [Viewer]   Checklist
│   └── 📖 ResearchPaper.pdf    [Editor]   Research
└── From Bob (1)
    └── 📄 Project Brief        [Editor]   Markdown
```

## 5. Markdown Editor / Viewer — UI & UX Audit

### Editor (`MarkdownEditor.jsx`)

#### What Works Well
- Auto-title extraction from first `# heading` line
- Tags, alerts, repeats, and attachments — feature parity with Notes
- Export (`.md`) and Print buttons
- 1 s auto-save with hash guard
- Attachment upload with size limit enforcement

#### Issues

**MD1 — Plain `<textarea>` with `font-mono` only**
The editor is a raw `<textarea>` with no syntax highlighting. Markdown tokens (`**bold**`, `## heading`) are invisible until the user switches to Preview. This makes writing Markdown uncomfortable compared to tools like Typora or Notion.

**MD2 — No formatting toolbar**
There are no Bold / Italic / Heading / Link / Code buttons. Users must know Markdown syntax or guess. This is a significant barrier for non-technical users.

**MD3 ✅ — Title derivation replaced with separate input field**
The fragile first-line title extraction was removed. A dedicated `<input>` field (Google Docs-style, 3xl bold, no border) now sits above the content `<textarea>`. Title and content are independent. The toolbar still shows the current title for orientation.

**MD4 ✅ — Edit/Preview toggle restored to local state**
The URL-navigation toggle was replaced with `setIsPreviewMode(v => !v)`. The `navigate` prop was removed from `MarkdownEditor`'s signature. The toggle is now instant with no route change.

**MD5 — No split view**
On desktop, side-by-side edit + preview is a standard expectation (VS Code, Typora, HackMD). The current toggle model requires switching back and forth to verify rendering.

**MD6 — Attachment thumbnails require decryption click to view filename**
Encrypted attachments show only an icon (no filename, no size, no type label) until the user clicks to decrypt and view. A filename badge should be visible without decryption.

**MD7 — Auto-scroll position not preserved across mode toggles**
When switching from edit to preview or back, the scroll position resets to the top. Long documents make this jarring.

**MD8 — No word count or reading time**
Both are trivial to compute and common in writing tools.

### Viewer (`MarkdownViewer`)

The viewer is used in both the Markdown app and the Research AI section. The component was not audited directly but from usage context:

**MD9 — No anchor navigation for headings**
Long documents have no table of contents or heading anchors.

**MD10 — Code blocks likely unstyled**
If `react-markdown` is used without `rehype-highlight` or `rehype-prism`, code blocks render as unstyled `<pre>` elements — no syntax highlighting.

**MD11 — Tables may not render**
Standard `react-markdown` does not support GFM tables without the `remark-gfm` plugin. If this plugin is absent, `|col|col|` tables render as raw text.

### Recommended Improvements

#### Near-Term (Low Effort)

| ID | Fix | Approach |
|----|-----|----------|
| ME1 ✅ | Fix title derivation | Separate `title` input field above the `textarea`, no longer auto-derived from content |
| ME2 | Add word count | `content.trim().split(/\s+/).length` displayed in footer |
| ME3 | Show filename on attachment thumbnails | Display `att.name` below each thumbnail icon even before decryption |
| ME4 ✅ | Restore local toggle | Reverted to `setIsPreviewMode(v => !v)`; `navigate` prop removed from `MarkdownEditor` |
| ME5 | Add GFM plugin | `npm install remark-gfm` → pass to `<ReactMarkdown remarkPlugins={[remarkGfm]}>` |

#### Medium-Term

| ID | Fix | Approach |
|----|-----|----------|
| ME6 | **Minimal formatting toolbar** | A fixed row of 6–8 buttons (B, I, H, list, code, link, quote) that wrap the textarea selection. No external lib required — pure string manipulation. |
| ME7 | **Syntax highlighting in editor** | Replace `<textarea>` with [CodeMirror 6](https://codemirror.net/) (`@codemirror/lang-markdown`). Adds ~120 KB but gives syntax highlighting, keyboard shortcuts, and bracket matching. |
| ME8 | **Scroll sync between edit/preview** | Track `textarea` scroll percentage; apply to preview `div` on toggle. |
| ME9 | **Code block highlighting in viewer** | Add `rehype-highlight` or `rehype-prism-plus` to the MarkdownViewer render pipeline. |

#### Long-Term

| ID | Fix | Approach |
|----|-----|----------|
| ME10 | **Split-view mode on ≥ md breakpoint** | Two-column layout: textarea left, MarkdownViewer right, both scrolling in sync. Behind a desktop-only toggle. |
| ME11 | **WYSIWYG mode** | Replace the edit surface with [Milkdown](https://milkdown.dev/) or [TipTap](https://tiptap.dev/) for a Notion-like block editor experience. Stores content as Markdown string for backwards compatibility. |

- Auto-sync research notes to Notes app "Research" folder
- BibTeX import and citation export (APA, MLA, IEEE, BibTeX)
- Tags, folder organisation, privacy/encryption toggles
- Collaboration support (E2EE per-document)

### Bugs

**R1 ✅ — `isShared` → `isSharedDoc` mismatch in `handleReadPdf`**
```js
// PaperEditor.jsx — was:
const fileKey = (paper?.isShared && paper?.docKey) ? paper.docKey : cryptoKey;
// Fixed:
const fileKey = (paper?.isSharedDoc && paper?.docKey) ? paper.docKey : cryptoKey;
```
`paper.isShared` was always `undefined`. PDFs in shared papers were always decrypted with the wrong key.

**R2 ✅ — Same bug in `handleGenerateAi`**
Same one-line fix applied to the AI generation path.

**R3 ✅ — PDF upload storage scope uses `paper.sharedId` (public link ID)**
```js
// Fixed:
const collabId = paper.collabShareId || paper.sharedId;
const scope = collabId ? `shared_docs/${collabId}` : (paper.workspaceId ? ... : `users/${user.uid}/research`);
```
Previously used only `paper.sharedId` (the public link ID). Newly uploaded PDFs on collaboration-shared papers now go to the correct `shared_docs/` storage path.

**R4 ✅ — `aiService` selector removed**
The dead service selector (`<select>` with only "Google Gemini") was removed from `PaperModals.jsx`. The model selector remains. The `aiService`/`setAiService` state was removed from `PaperEditor`.

**R5 ✅ — IEEE citation replaced with proper manual formatter**
Replaced the Vancouver-template fallback with a manual IEEE formatter that uses the CSL-JSON data from `cite.data[0]` to produce `I. Lastname, "Title," Journal, Year.` style output.

**R6 ✅ — PDF chip now clickable in both edit and preview mode**
```jsx
// Fixed: removed the isPreviewMode condition
<span className="cursor-pointer" onClick={handleReadPdf}>
```

### Performance Issues

**P1 ✅ — `findOrCreateFolder` reads all docs on every mount**
`PaperEditor` had a `useEffect` that called `getDocs` on both `notes` and `markdown` collections on every mount. Fixed by caching the resolved folder IDs in `sessionStorage` keyed by `research_folder_{collection}_{uid|workspaceId}`. Subsequent mounts skip the `getDocs` entirely until the session ends.

**P2 ✅ — Partially addressed via P1 caching**
The `findOrCreateFolder` fix covers the notes and markdown folder scans. The `getOrCreateAiPromptsFolder` scan is a separate call and is not yet cached — see P3 below.

> **Note:** `localStorage`-based TTL cache was replaced with `sessionStorage` (no TTL needed — session lifetime is appropriate for folder IDs that don't change).

**P3 — Three concurrent Firestore reads before paper is usable**
On mount: (1) notes folders, (2) markdown folders, (3) AI prompts. These run in parallel but all block the Gemini API being usable. Consider lazy-loading the AI prompts only when the AI section is first expanded.
